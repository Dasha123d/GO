# Безопасность Casbin: лучшие практики

## 1. Используйте явное deny при необходимости

Модель с приоритетом deny:
```ini
[policy_effect]
e = priority(p.eft) || deny
```
Это гарантирует, что если есть deny-правило, оно перекроет allow, даже если allow стоит первым.

## 2. Не доверяйте только matcher
Помните, что matcher выполняется для каждого правила. Избегайте сложной логики, которая может привести к обходу.

## 3. Защитите модель и политики
* Файлы `model.conf` и `policy.csv` не должны быть доступны наружу (не кладите в публичные директории).
* В production используйте БД с контролем доступа, а не файлы.

## 4. Валидируйте запросы
Прежде чем передавать в `Enforce`, убедитесь, что параметры (`sub`, `obj`, `act`) очищены от инъекций. Например, `obj` не должен содержать `..` или спецсимволы, если используется `keyMatch` с путями.

## 5. Не используйте `keyMatch` без ограничений
Шаблоны типа `/*` могут дать доступ ко всему. Явно указывайте разрешённые пути для ролей, старайтесь избегать wildcard в критических местах.

## 6. Фильтруйте политики для каждого пользователя
При большом количестве правил загружайте только нужные через `LoadFilteredPolicy`, чтобы избежать утечек данных через память (если кешируете).

## 7. Логируйте отказы
Записывайте все случаи, когда `Enforce` возвращает `false`, с информацией о пользователе, объекте и действии. Это поможет в расследовании инцидентов.

## 8. Обновляйте политики через безопасный API
Не позволяйте пользователям напрямую менять БД политик. Используйте внутренний сервис с проверкой прав администратора.

## 9. Тестируйте модель
Проверяйте все сценарии доступа: пользователь, роль, наследование, deny-правила. Casbin позволяет юнит-тестировать правила через тестовый фреймворк.

## 10. Следите за производительностью
При очень большом количестве правил matcher может стать узким местом. Рассмотрите кеширование решений (RBAC с ролями кешируется Casbin автоматически).
