# Тюнинг производительности fasthttp

## Особенности архитектуры

- **Переиспользование объектов:** `RequestCtx`, `Request`, `Response` аллоцируются из пулов. Никогда не сохраняйте ссылки на них за пределами обработчика.
- **Zero-copy:** По возможности работайте с телом запроса/ответа через `ctx.Request.Body()` / `ctx.Response.BodyWriter()` без лишних копирований.
- **Не копируйте `RequestCtx`:** Передавайте контекст по указателю, не клонируйте.

## Оптимальные настройки сервера

```go
s := &fasthttp.Server{
    Handler:               handler,
    Concurrency:           256 * 1024, // максимум горутин-обработчиков
    ReadBufferSize:        4096,       // размер буфера чтения
    WriteBufferSize:       4096,       // размер буфера записи
    TCPKeepalivePeriod:    30 * time.Second,
    MaxRequestBodySize:    4 << 20,    // ограничивайте размер
}
```
Подбирайте `ReadBufferSize`/`WriteBufferSize` под средний размер запросов/ответов (обычно 4096-16384).

## Пайплайнинг и Keep-Alive
Fasthttp по умолчанию держит keep-alive соединения, что уменьшает количество рукопожатий. Увеличьте `MaxConnsPerIP`, если много клиентов за NAT.

## Сжатие ответов
Сжимайте на лету через `compress` пакет, но помните, что сжатие добавляет CPU-нагрузку. Для статики лучше отдавать предварительно сжатые файлы.

## Пул горутин
Fasthttp сам управляет горутинами через внутренний воркер-пул. Параметр `Concurrency` ограничивает максимальное количество одновременно обрабатываемых запросов. Не делайте его слишком большим без необходимости — иначе память утечёт при медленных клиентах.

## Метрики
Используйте `fasthttp/pprof` для просмотра внутренних метрик (количество активных соединений, количество запросов в пуле).

## Сравнение с net/http
* Меньше аллокаций (нет `http.Request`, `http.Response` на каждый запрос).
* В 5-10 раз выше пропускная способность на тех же ресурсах.
* Несовместим с middleware, написанными для `net/http`.
