# Безопасность ants: лучшие практики

## 1. Всегда обрабатывайте панику

```go
pool, _ := ants.NewPool(100,
    ants.WithPanicHandler(func(i interface{}) {
        log.Printf("восстановлен паника: %v\n%s", i, debug.Stack())
        // метрика или оповещение
    }),
)
```
Без обработчика паника в задаче уронит весь процесс.

## 2. Корректно завершайте пул
```go
defer pool.Release()
```
`Release()` ждёт завершения всех принятых задач и останавливает воркеры. В асинхронных сценариях при завершении приложения дождитесь `pool.Wait()` перед Release.

## 3. Не забывайте про `WaitGroup` при использовании `Submit`
Если вы отправляете задачи в цикле и сразу выходите из функции, пул может не успеть их выполнить. Либо используйте `pool.Wait()` (только для `PoolWithFunc`), либо внешний `sync.WaitGroup`.

## 4. Не передавайте примитивы синхронизации в задачи без необходимости
Замыкания с `wg.Add(1)` внутри цикла безопасны, если переменная `i` скопирована. Внимание на гонку данных.

## 5. Защита от deadlock при `Nonblocking=false`
Если все горутины пула ждут друг друга, пул может застрять. Проектируйте задачи так, чтобы они не зависели от других задач в том же пуле.

## 6. Размер очереди и обратное давление
Ограничивайте `MaxBlockingTasks`. Слишком большая очередь приводит к нехватке памяти и долгому ожиданию. Лучше быстро вернуть ошибку (HTTP 429) при переполнении.

## 7. Таймауты в задачах
Если задача может зависнуть (сеть, БД), оборачивайте её в собственный контекст с таймаутом, чтобы не занимать горутину вечно.

## 8. Обновляйте ants
Библиотека стабильна, но обновления могут приносить исправления утечек. Фиксируйте версию в `go.mod` и проверяйте changelog.

## 9. Не изменяйте размер пула бездумно
`Tune` может временно создавать много горутин при резком увеличении. Лучше изначально выделить достаточный размер.

## 10. Логируйте ошибки
Используйте `WithLogger` для контроля внутренних проблем (например, превышение лимита при `Nonblocking`).
